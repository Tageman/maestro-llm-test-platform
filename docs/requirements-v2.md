## 1. 文档定位

| 项目 | 约定 |

本轮依据已讨论的页面可操作性、重复执行能力和后续规划形成产品需求，不增加一期发布门禁，也不重新启动 M4 验收。原建议中的“V1.1 可用性 / V1.2 稳定复跑 / V2 效率能力”统一命名为 V2-A、V2-B、V2-C，避免产品版本与历史里程碑混淆。

V2 的目标是：测试人员不依赖终端或重新上传 Excel，就能找到已有用例、选择已批准版本、执行、理解失败并再次执行；每次执行仍有独立、可追溯的证据。

## 2. 现状与问题

| 当前基础 | 主要缺口 | V2 处理方向 |
| --- | --- | --- |
| Excel 校验、IR/YAML 生成和审批 | 页面上下文主要在内存，没有工作簿和生成版本历史入口 | 持久资源导航、刷新恢复、版本详情 |
| 同一 ready Generation 可创建多个 Run，后端已有 case_ids | 页面没有完整的再次执行、失败重跑、选例执行操作 | 暴露已有能力并补安全选择语义 |
| Run 查询、事件接口、Case 详情和产物下载 | 运行视图主要轮询；运行中 Case 状态与错误指引不足 | 实时状态、分层错误、下一步操作 |
| 跨 Case Fixture、重试轮次和退出恢复 | 使用者难以判断上次清理是否完成、当前环境是否可复用 | 运行前检查、清理风险提示、状态契约 |
| Run 内受控定位修复 | 修复结果不会自动成为下一 Run 的批准版本 | 经差异审查生成新版本，禁止悄悄覆盖 |

依据为 `frontend/src/App.tsx`、`frontend/src/features/runs/RunConsole.tsx`、`frontend/src/api.ts` 及后端 RunService/Repository；这是代码层面的现状核对，不声称已经完成新一轮交互或设备实测。

## 3. 用户流程与产品边界

主流程：工作簿历史 → 工作簿详情及校验 → 生成版本及审批 → 选择 Case / 确认执行计划 → 运行前检查 → 执行详情 → 结果下载或新建重跑。

两个概念必须区分：

- **方便重复执行**：复用批准版本、减少重复上传和生成操作；仍创建新的 Run，不承诺免除 pytest 或设备执行耗时。
- **结果可重复**：在相同执行版本、明确的 App/账号/页面/数据条件下执行；环境不满足时明确阻断，不能靠反复重试获得绿色结果。

本期保留 Excel 三 Sheet、Flow IR、确定性 YAML 编译、pytest 生命周期、Maestro CLI 执行和 MCP 受控诊断路线。不重做执行引擎，不扩大自动修复为任意业务步骤修改。

## 4. 功能需求

### 4.1 V2-A：日常操作闭环（P0）

| ID | 需求 | 明确行为 |
| --- | --- | --- |
| V2-R01 | 历史入口 | 列出工作簿、生成版本和 Run；支持名称/ID、状态、时间等适用筛选和分页；显示空态、加载失败和损坏记录提示 |
| V2-R02 | 页面恢复 | 工作簿、生成详情、Run 均有稳定链接；刷新、前进后退恢复资源和已保存审批，不依赖之前页面内存；未保存的选择不冒充已保存 |
| V2-R03 | 选例执行 | 按模块、标签、关键字筛选并勾选 Case；显示选择数量、Fixture 依赖和实际执行顺序；空选择禁止执行，未生成/未批准的流程明确阻断 |
| V2-R04 | 再次执行 | 终态 Run 可“按原范围再次执行”或“重跑失败”；预览版本、范围、状态条件及风险；新 Run 关联来源，不覆盖旧 Run，不默认重新调用 LLM |
| V2-R05 | 可理解的运行详情 | 显示当前 Case、前置/业务/清理阶段、Attempt、修复与导出进度；业务结果、清理结果、环境异常分别表达；有取消与产物下载入口 |
| V2-R06 | 可行动错误 | 区分服务不可用、设备不可用、页面条件不符、生成/审批阻断、业务失败、清理和导出失败；说明原因、相关证据和下一步；禁止笼统“重试即可” |
| V2-R07 | 防误操作 | 双击/网络重试不创建重复 Run；运行中禁止重复提交；错误后保留当前上下文；移除用户主流程中的 M1/M3 等研发阶段术语 |

操作细则：

1. “按原范围再次执行”复用来源 Run 的 Generation 与 selected_case_ids，不因后来新增 Case 扩大范围。终态失败或取消 Run 均可发起，但须经过执行资格与设备检查。
2. “重跑失败”默认选取 `FAILED / FIXTURE_FAILED / ENV_ERROR / TIMEOUT`；被前置失败阻断的 `BLOCKED`、提前停止或取消导致未执行的 `PENDING` 单列为可勾选项，默认不偷偷包含。取消是 Run 状态，不虚构 Case 的 CANCELLED 状态。
3. 若 Run 只有导出失败、没有失败 Case，显示“没有可重跑失败项”；不能把空集合解释为全量执行。导出错误提供下载既有证据/排障，不通过重跑业务掩盖。
4. 选择 Case 只要求其 Fixture 依赖闭包，不自动加入其它业务 Case。若用户业务依赖另一 Case，应改为显式 Fixture 或明确数据前提；平台不推断隐式业务依赖。
5. 页面按钮是否可点只是提示，后端必须再次校验批准状态、版本完整性、设备占用和输入合法性。

### 4.2 V2-B：稳定复跑（P1，依赖 V2-A）

| ID | 需求 | 明确行为 |
| --- | --- | --- |
| V2-R08 | 环境预检 | 分别显示后端、CLI、ADB/目标模拟器、目标 App、版本与基线条件；设备在线不等于页面可操作；每项为 pass / fail / unknown，并给证据时间 |
| V2-R09 | 运行状态契约 | 为执行配置声明页面/账号/数据前提、准备 Fixture、清理要求；支持保留数据或已批准的重建/清理；默认不清数据、不更换账号、不重置设备 |
| V2-R10 | 清理与重试约束 | 上次相关 Run 清理 failed/unknown 时提示并要求重新检查/显式恢复；新 Run 从完整 Fixture 生命周期开始；禁止复用前一次进程内 Fixture 缓存 |
| V2-R11 | 版本与结果比较 | 对比同一 Generation 的两次 Run 的 Case、Attempt、业务结果、清理和耗时；不同版本显示版本差异与不可直接比较原因；保留每次执行证据 |

预检不是万能证明。只有可机器验证的条件才显示通过；账号或数据无法验证时显示 unknown，review 模式需人工确认并留时间/说明，无人值守模式遇到必需条件 unknown 必须停止。人工确认只是确认记录，不伪装为机器验证通过。

App 启动、清数据、登录、数据创建等会改变状态的动作必须来自用户批准的 Fixture/执行配置；预检本身只读，不自动关闭弹窗或用其它 App 替换验收对象。

### 4.3 V2-C：配置、版本复用与效率（P2，依赖前两阶段）

| ID | 需求 | 明确行为 |
| --- | --- | --- |
| V2-R12 | 生成策略配置 | 页面选择内置规则或已配置的 LLM Profile；显示模型、服务地址、连接状态、参数和生成来源；密钥只存服务端，页面仅显示已配置/掩码；切换策略生成新版本 |
| V2-R13 | 修复提升为版本 | 选择有成功验证证据的受控修复，预览源步骤/IR/YAML 差异及影响的 Fixture 消费者；提升为派生 Generation，经语法校验和人工审批后方可复用 |
| V2-R14 | 耗时与有限批量复跑 | 展示生成、预检、Fixture、Case、诊断、导出耗时；对已批准计划设置有限次数串行执行，默认 1 次、上限 20 次，任一失败停止；支持取消并保留每轮结果 |

规则模式与 LLM 模式沿用同一 IR 校验与确定性编译门禁。修复提升不得删除/放宽断言、写回源 Excel、直接接受任意 YAML 或覆盖已批准版本。批量复跑用于稳定性观察，不允许“直到成功”为停止条件。

## 5. 信息架构与界面要求

| 页面 | 主操作 | 必须展示 |
| --- | --- | --- |
| 工作簿库 | 上传、搜索、打开 | 文件名、导入时间、校验状态、生成/执行入口 |
| 工作簿详情 | 查看校验、生成版本、选择用例 | 三 Sheet 摘要、字段错误位置、模块/标签、版本历史 |
| 生成详情 | 预览与审批、执行选中 Case | 来源、生成策略、IR/YAML、warning、审批状态、依赖 |
| 执行确认 | 确认范围、预检、执行 | 版本、Case 顺序、Fixture 闭包、设备/App、状态风险 |
| 运行历史 / 详情 | 查看、取消、重跑、比较、下载 | 业务/清理/环境状态、来源 Run、实时进度与证据 |
| 设置（V2-C） | 配置生成 Profile | 非敏感配置、密钥配置状态、显式连接测试 |

所有关键操作须有明确 loading/disabled/empty/error 状态；disabled 必须解释原因。错误不得清空当前选择。颜色不作为唯一状态区分方式；关键操作支持键盘和可辨识的控件名称。结构化日志是诊断补充，不能成为普通用户理解运行状态的唯一入口。

## 6. 数据和非功能约束

- 源 Excel、已批准版本及历史 Run 证据不可被重跑覆盖；源文件内容改变应重新导入，不按同名文件覆盖。
- 新 Run 独立存储，记录来源 Run、执行范围、实际配置及版本指纹。Run 内修复仅影响该 Run，除非走显式版本提升。
- 单运行锁、设备绑定、受控修复、Fixture 生命周期和退出恢复继续有效。服务重启只恢复可查看状态/审计，不自动续跑旧业务。
- 支持原有相对输出目录和用户指定绝对导出目录；新导出文件须含 Run ID，冲突时不得静默覆盖；运行证据仍保留于受管 Run 目录。
- 本地健康磁盘是支持范围；网络盘失联、完整操作系统重装、多用户权限体系不纳入 V2-A/B 的必达目标。
- 性能目标（待实施测量，不是当前实测结果）：在记录配置的本地开发机、健康本地磁盘、1,000 条历史记录数据集下，历史首屏请求 p95 ≤ 1 秒，交互可用 ≤ 2 秒；正常连接下已落盘运行事件在页面可见的 p95 ≤ 2 秒。至少采样 30 次，冷启动单独记录；设备/LLM 执行耗时单独报告，不设虚假的总耗时承诺。
- 新增前端端到端测试覆盖上传到重跑的关键交互；测试替身验证 UI/协议，真实设备验证执行行为，二者证据不能混称。

| V2-AC06 / R09～R11 | 相同批准版本及显式基线连续两轮；核对每轮 Fixture 次数、清理、版本和比较结果；注入清理异常验证下一轮阻断 | 两个 Run、Fixture trace、配置/版本指纹、比较报告；失败注入可用测试替身 | 跨 Run 缓存 Fixture、清理失败后继续批量执行、不同版本误称同基线 |
| V2-AC07 / R12 | 切换规则/LLM Profile、检查失败输出；查看页面、API、日志无密钥；新生成记录策略来源 | 配置/API/UI 测试、脱敏扫描、一次可用 LLM 的受约束输出记录（费用/凭据由用户提供） | 泄露密钥、绕过 IR 校验、把模拟调用冒充真实 LLM；无凭据则标 BLOCKED 而非 PASS |
| V2-AC08 / R13 | 将一个成功受控修复提升为新版本，查看差异、校验、人工审批并执行；再检查原版本 | 修复/派生版本关联、IR/YAML 一致性测试、审批及新 Run，原始哈希 | 断言弱化、未审批执行、源 Excel/旧版本改变、共享 Fixture 影响未展开 |
| V2-AC09 / R14 | 串行执行固定 3 轮，另测第 2 轮失败和中途取消；核对耗时和结果数量 | 批量调度测试、父批次/子 Run 记录、耗时明细 | 并发占设备、失败后继续下一轮、取消后派发、覆盖失败轮次或无限重试 |

收束规则：

1. 每阶段固定一个候选 commit、输入哈希、环境信息、验收表和证据索引；复用同一版本已有证据。新修改只复验受影响项，注明失效原因。
2. 真实设备阶段开始先做一次环境检查；遇环境问题停止并标 BLOCKED。定位并修正明确原因后允许一次定向复验；仍失败则报告原因和下一步，不在同一轮无上限尝试。
3. 不通过换 App、放宽断言、清空失败记录或未授权重置设备来“验收通过”。设备不满足条件与平台缺陷分开记录，但都不能写为 PASS。
4. 自动化测试数和构建成功不等于用户走查通过；每阶段一次集中走查，由用户确认结论，不新增循环审批流程、不代签。旧 M4 记录保持原有含义。
5. 本次交付仅为文档整理及 Git 提交/推送，不执行上述验收，也不宣布 V2 或 M4 已发布。

## 8. 后续方向与非目标

V2-A/B 优先解决可用性和复跑，不被智能化扩展阻塞。V2-C 可独立排期。以下仅作为后续方向，不计入本轮必达验收：Android 真机、多设备并行/设备池、CI 定时任务、远程部署和团队权限、跨平台 iOS、视觉模型泛化定位、跨项目数据平台。

不承诺自动识别所有中文句式、任意 App 业务状态自动恢复、破坏性操作天然幂等，或任意两轮业务结果必定相同。业务前提、数据权限和可验证期望仍需由用例作者明确。
