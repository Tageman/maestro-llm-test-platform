## 2. 技术设计兼容修订

### 2.1 审批来源与历史数据

`GeneratedFlowDetail.approval_method` 新增可选值 `automatic | manual | null`。人工批准明确记录 `manual`；历史 warning 批准若缺乏这一证据，保留生成材料但降级待确认。即使缓存 Generation 摘要仍为 `ready`，创建 Run 也会逐项验证 Flow 的语法、状态和审批来源。

该规则替代旧技术设计中“无人值守语法通过即可自动 ready”的表述，落实原有 warning 人工复核门禁。Flow IR 1.0、原请求模式、运行状态图保持不变；API V1.1 增量增加字段。

### 2.2 默认启动与显式 Fixture 优先级

系统启动 Flow 的来源是 `Config.launch_clear_state`，单独保存在 `generated/system/default-launch.yaml`，不伪造用户 Excel 行或改写批准后的 Case/Fixture。`generated/mappings/pytest.json` 的 `startup_plans` 记录是否启用、显式接管 Flow 和配置值。

默认启动前先注册后置清理，以便启动或前置失败后仍执行既定清理。系统启动纳入 trace 和进程超时预算。纯 function 包每 Attempt 启动；共享包每轮启动一次，重试前清理并重建整轮。短作用域启动、跨 Case 不一致的显式启动计划阻断生成，防止破坏共享初始化。

### 2.3 目录导出与执行结果分离

- 权威证据仍在 `RUNTIME_DIR/runs/<run_id>/`；交付目录是副本，不移动或删除原始证据。
- 相对路径基准固定为项目根目录，不依赖启动终端的当前目录；支持 `~` 展开后的绝对目录。用户指定目录须由后端进程有权写入。
- 拒绝 `..`、符号链接路径、与当前 Run 重叠的目标，以及已存在的 `<run_id>` 目录；不覆盖用户现有文件。
- `Run` / `RunSummary` 增加 `export_status`、`export_path`、`export_error`。终态后前端继续等待导出结束。导出失败只标记交付失败，不把已通过的业务用例改为失败。
- 复制期间保留 `.export-incomplete`；完成文件复读哈希检查和 `export-manifest.json` 后才移除此标记。失败残留供人工检查，不自动删除。
- 导出是交付时快照：副本 `run.json` 记录成功交付状态，其余证据保持生成时内容（包括导出前的 `result/summary.json`）。导出完成事件记录在权威 Run，不追写副本；以 `run.json` / API 判断当前交付状态。
- 本机目录防误写检查不是跨用户恶意并发攻击下的文件系统隔离机制；本次不新增远程多用户部署能力。

### 2.4 Fixture 结果语义

仅从已注册、路径和 SHA-256 均验证通过的 trace 读取执行事件。Fixtures K～Q 显示最后一次观测到的执行结果：`PASSED / FAILED / INTERRUPTED / NOT_RUN / DISABLED`；无完整结束证据不得判为成功。当前 Fixture 不参与 Case 定位自动修复，所以自动修复次数为 0。

完整执行历史仍在 trace 中；`result/writeback-manifest.json` 增加 `verified_fixture_rows` 与 `fixture_execution_counts`。源 Excel 不变，旧结果列会被清空或替换，生成路径只有确实存在才写入。复读验证覆盖本次写入的每一个结果单元格。

1. **R08 已实现并回归**：按技术设计 V1.3 落实共享作用域、启动与重试规则；继续按当前构建记录设备验收，而非重复开发。

3. **当前版本真实模拟器验收**：锁定构建、Excel 哈希和设备，按 M4-AC-01～04 留下 review/unattended、失败停止、启动、Fixture、修复和导出证据。没有设备只能标记未执行/阻断，不可判通过。
4. **独立走查与签收**：非开发者按说明书操作，产品/测试负责人裁决 M4-AC-05/06；自动化不能替代签名。
